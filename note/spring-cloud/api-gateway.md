# Примеры фильтров

Да, такой вариант не просто возможен, а очень часто применяется на практике!
Это обратная ситуация: вы хотите, чтобы для внешнего мира (мобильного приложения
или фронтенда) ссылки оставались максимально короткими и простыми
(/users/create), а внутри микросервиса используется строгая версионность и
архитектурные стандарты (/api/v1/users/create).
Для реализации этой задачи в Spring Cloud Gateway есть два пути: с помощью уже
знакомого вам фильтра RewritePath или через специальный фильтр PrefixPath [^1].


## Вариант 1. Через фильтр PrefixPath (Самый элегантный)

Если вам нужно просто «дописать» ко всем входящим запросам одинаковое начало,
фильтр PrefixPath сделает это идеально. Он берет оригинальный путь клиента и
вставляет указанный префикс в самый старт [^1].

```yaml
          routes:
            - id: user-service-internal-prefix
              uri: http://localhost:8081
              predicates:
                - Path=/users/**                  # 1. Ловим простой внешний путь
              filters:
                - PrefixPath=/api/v1              # 2. Невидимо для клиента добавляем префикс в начало


```

Как это работает по шагам:

1. Клиент отправляет запрос: POST http://localhost:8080/users/create
2. Гейтвей видит, что путь начинается с /users/ (условие сработало).
3. Фильтр PrefixPath=/api/v1 берет оригинальный путь /users/create и превращает
   его в /api/v1/users/create.
4. Внутренний микросервис получает запрос по
   адресу: http://localhost:8081/api/v1/users/create.
5. Срабатывает ваш контроллер:

@RestController
@RequestMapping ("/api/v1/users")public class UserController {
@PostMapping ("/create")
public ResponseEntity<Void> createUser () { ... }
}

## Вариант 2. Через фильтр RewritePath (Если нужна гибкость)

Если логика подстановки путей сложнее, можно использовать регулярные выражения,
которые вы видели в учебнике. Мы ловим часть пути и пересобираем строку заново.

```yaml
          routes:
            - id: user-service-flexible-rewrite
              uri: http://localhost:8081
              predicates:
                - Path=/users/**
              filters:
                # Находим всё, что идет после слэша, и конструируем новый внутренний путь
                - RewritePath=/users/(?<segment>.*), /api/v1/users/${segment}

```

Как это работает здесь:

1. Клиент шлет: /users/create
2. Регулярное выражение захватывает слово create в переменную segment.
3. Фильтр подставляет её в шаблон: /api/v1/users/create.
4. Результат абсолютно такой же, как и в первом варианте.

## Почему это хорошая практика?

* Безопасность: Внешние пользователи не знают реальную структуру папок и
  эндпоинтов внутри вашей сети.
* Удобство рефакторинга: Если завтра вы решите обновить микросервис до версии
  /api/v2/users, вам не придется менять код на фронтенде или перевыпускать
  мобильное приложение. Вы просто измените одну строчку в application.yml
  гейтвея: - PrefixPath=/api/v2, и клиенты даже ничего не заметят.

Хотите попробовать объединить это в один готовый файл application.yml, в котором
будут настроены оба микросервиса (с добавлением заголовков, отсечением или,
наоборот, добавлением префиксов)? Могу составить чистый и рабочий конфиг без
ошибок из учебника.

---

Да, конечно! Вы можете без каких-либо проблем объединять фильтры PrefixPath и
AddRequestHeader внутри одного маршрута.
В Spring Cloud Gateway фильтры работают по принципу цепочки (Chain). Они
выполняются один за другим в том порядке, в котором вы их записали в
конфигурационном файле [^1].
Ваш рабочий application.yml будет выглядеть так:

          routes:
            - id: user-service-combined
              uri: http://localhost:8081
              predicates:
                - Path=/users/**
              filters:
                - PrefixPath=/api/v1
                - AddRequestHeader=X-Request-ID, demo-header

## Как Гейтвей обработает этот запрос (по шагам):

1. Шаг 1 (Вход): Клиент делает запрос POST http://localhost:8080/users/create.
2. Шаг 2 (Фильтр 1): Срабатывает PrefixPath. Путь превращается в
   /api/v1/users/create.
3. Шаг 3 (Фильтр 2): Срабатывает AddRequestHeader. В запрос незаметно вшивается
   заголовок X-Request-ID: demo-header.
4. Шаг 4 (Выход): Микросервис получает измененный запрос на
   адрес http://localhost:8081/api/v1/users/create вместе с добавленным
   HTTP-заголовком.

Внутри вашего WebMVC-микросервиса вы сможете одновременно принять этот запрос в
контроллере @RequestMapping ("/api/v1/users") и прочитать сгенерированный
заголовок через аннотацию @RequestHeader:

@PostMapping ("/create")public ResponseEntity<Void> createUser (@RequestHeader (
"X-Request-ID") String requestId) {
// Вы увидите в консоли: "Получен запрос с ID: demo-header"
System.out.println ("Получен запрос с ID: " + requestId);
return ResponseEntity.ok ().build ();
}

Теперь, когда оба фильтра настроены вместе, вы хотите добавить второй
микросервис для заказов (order-service) в этот же конфигурационный файл или
перейдем к тестированию через Postman / cURL?

# Как работает ответ через фильтры

Представьте, что фильтр — это контрольно-пропускной пункт (КПП) на въезде на
закрытую территорию фабрики (ваших микросервисов).
Когда машина (запрос) едет внутрь, охранник проверяет документы и вешает на
лобовое стекло пропуск. Это обработка входящего запроса (фаза Pre).
Но когда эта же машина едет обратно, она снова обязана проехать через этот же
КПП! Охранник может остановить её, проверить груз, поставить штамп «Выезд
разрешен» или выдать водителю чек. Это обработка исходящего ответа (фаза Post).
В коде гейтвея это работает точно так же. Когда микросервис закончил работу и
отдал ответ (например, JSON с данными и статус 200 OK), этот ответ не летит
клиенту напрямую. Он сначала возвращается в Gateway, проходит через фильтры в
обратном порядке, и только потом отдается клиенту.


## Зачем фильтру обрабатывать ОТВЕТЫ? (Реальные примеры)

Вот 4 самые частые задачи, которые делают с ответами на гейтвее:

1. Добавление глобальных заголовков безопасности (Security Headers)
   Чтобы не прописывать в каждом микросервисе заголовки вроде X-Frame-Options:
   DENY (защита от встраивания вашего сайта во фреймы) или настройки
   кэширования, гейтвей может автоматически штамповать их на все ответы всех
   микросервисов.
2. CORS (Cross-Origin Resource Sharing)
   Если ваш фронтенд (например, на React или Angular) запущен на другом домене,
   браузер заблокирует ответы от бэкенда, если в них нет заголовка
   Access-Control-Allow-Origin. Гейтвей перехватывает ответ микросервиса и
   добавляет этот заголовок перед отправкой в браузер.
3. Логирование и метрики времени выполнения
   Фильтр засекает время в фазе Pre (когда запрос вошел), а в фазе Post (когда
   ответ вернулся от микросервиса) вычитает одно из другого. Так мы узнаем
   точное время работы микросервиса и пишем в лог: «Запрос /users обработан за
   45мс со статусом 200».
4. Маскирование ошибок
   Если внутри микросервиса упала база данных и он выдал страшную ошибку 500
   Internal Server Error с кучей системного текста (стэк-трейсом), гейтвей может
   перехватить этот ответ, стереть опасные технические детали и вернуть клиенту
   аккуратный JSON: {"error": "Что-то пошло не так, попробуйте позже"}.


## Как это выглядит в конфигурации application.yml?

Для обработки ответов в Spring Cloud Gateway есть встроенные фильтры. Обратите
внимание на их названия — они начинаются со слова Response:

          routes:
            - id: user-service-response-demo
              uri: http://localhost:8081
              predicates:
                - Path=/users/**
              filters:
                - PrefixPath=/api/v1                 # [Pre] Меняет входящий путь
                - AddRequestHeader=X-Request-ID, 123 # [Pre] Добавляет заголовок в запрос
                # ----------------------------------------------------
                - AddResponseHeader=X-Author, MavenUchebnik # [Post] Добавит заголовок в ОТВЕТ клиенту

Если вы сделаете запрос, то в браузере или Postman во вкладке Headers (Заголовки
ответа) вы увидите X-Author: MavenUchebnik, хотя сам микросервис user-service об
этом заголовке даже не догадывается.
Стало ли теперь понятнее, как Гейтвей работает в обе стороны (туда и обратно)?
Хотите посмотреть, как эта магия "до и после" пишется на чистом Java-коде, если
встроенных фильтров из yml файла становится мало?

# Маршрутизация Istio + Spring Cloud Gateway

Да, вы абсолютно правильно всё понимаете! Логика движения и обработки пути распределяется именно так.
Отвечая на первый вопрос: да, вместо mysite.com можно и нужно указать localhost (или просто оставить универсальную звездочку *), чтобы успешно тестировать всё на вашем компьютере без ковыряния системных файлов.
Давайте пошагово разберем, как выглядит этот конвейер обработки пути в деталях:


## 1. Как localhost заменяет mysite.com в VirtualService
Если в манифесте написать hosts: ["mysite.com"], то Istio будет обрабатывать запрос только в том случае, если в заголовках HTTP (Header Host) прилетит именно это имя. Для локальной разработки в Minikube проще написать:

spec:
  hosts:
    - "localhost" # 👈 Теперь Istio будет легально ловить запросы к localhost
  gateways:
    - app-gateway

------------------------------
## 2. Пошаговый путь запроса http://localhost/api/tasks
Вот как этот адрес распиливается и обрабатывается на двух рубежах:
## Рубеж 1. Работа Istio (Перехват по префиксу /api)

   1. Вы отправляете в Postman запрос: GET http://localhost/api/tasks.
   2. Шлюз Istio Ingress Gateway принимает его на порту 80 благодаря запущенному minikube tunnel.
   3. Istio смотрит в VirtualService и сверяет путь. В конфиге написано: prefix: /api.
   4. Так как ваш путь /api/tasks начинается с /api, условие выполняется!
   5. Istio, ничего не меняя в адресе, пересылает исходный запрос http://localhost/api/tasks на вход вашего Java-приложения spring-cloud-gateway на порт 8080.

## Рубеж 2. Работа Spring Cloud Gateway (Обработка внутренностей)
Теперь запрос целиком внутри Java. Задача шлюза — понять, какому микросервису отдать этот /tasks. Поскольку в учебнике конфигурация Spring Cloud Gateway пропущена, вот как должен выглядеть его application.yml, чтобы этот конвейер заработал:

spring:
  cloud:
    gateway:
      routes:
        - id: tasks-route
          # 1. Говорим, куда перенаправить (внутреннее DNS-имя сервиса задач в K8s)
          uri: http://cluster.local
          # 2. Предикат: ловим запросы, которые пришли на шлюз по этому пути
          predicates:
            - Path=/api/tasks/**
          # 3. Фильтр: отрезаем технический префикс /api, чтобы не спамить им Java-код
          filters:
            - StripPrefix=1 

## 🔄 Что делает фильтр StripPrefix=1?
Если оставить запрос как есть, Spring Cloud Gateway отправит в tasks-service путь /api/tasks. Но ваш TaskController в Java настроен на @RequestMapping("/tasks") (без слова /api).
Фильтр StripPrefix=1 берет путь /api/tasks, отрезает от него первую часть (то есть /api) и отправляет в tasks-service чистый, красивый путь /tasks.

## Резюме конвейера:

   1. Вы шлете: /api/tasks
   2. Istio видит /api, пропускает запрос целиком внутрь кластера и отдает шлюзу: /api/tasks.
   3. Spring Cloud Gateway перехватывает /api/tasks/**, отрезает кусок /api и превращает его в /tasks.
   4. tasks-service получает чистый путь /tasks и успешно возвращает вам список объектов со статусом 200 OK.

# cluster.local

cluster.local — это главный внутренний интернет-домен вашего кластера Kubernetes.
Точно так же, как в обычном интернете все сайты заканчиваются на .com, .ru или .org, внутри любого кластера Kubernetes все сервисы по умолчанию получают адреса, заканчивающиеся на .cluster.local. Этот домен обслуживается встроенной в Minikube службой CoreDNS (локальным провайдером кластера).
Чтобы этот адрес больше не выглядел как заклинание, давайте распилим его по кусочкам справа налево:
tasks-service . default . svc . cluster . local

   1. .local — указывает, что этот адрес является локальным и приватным. Компьютеры из обычного интернета не могут открыть такой сайт.
   2. .cluster — подтверждает, что адрес принадлежит внутренней сети Kubernetes.
   3. .svc — сокращение от Service. Это системный маркер кластера, говорящий, что этот домен ведет именно на сетевой объект Service, а не на отдельный Под или виртуальную ноду.
   4. .default — это имя пространства имен (Namespace), той самой «виртуальной папки», где лежит ваше приложение. Если бы сервис лежал в папке prod, адрес бы изменился на .prod.svc....
   5. tasks-service — имя конкретного Kubernetes Service, которое вы сами написали в YAML-манифесте в поле metadata.name.


## Зачем писать этот адрес целиком?
Когда микросервисы лежат в одной папке (default), они могут вызывать друг друга по короткому имени: http://tasks-service. Kubernetes сам допишет остаток.
Но когда в систему включается Istio Ingress Gateway (который живет в своей изолированной папке istio-system), его встроенные прокси-серверы Envoy не могут угадать, в какой папке искать tasks-service. Чтобы трафик гарантированно долетел с сетевого шлюза до вашего Java-приложения, Istio требует указывать полное имя (Fully Qualified Domain Name — FQDN).
Прописав tasks-service.default.svc.cluster.local, вы дали шлюзу точные географические координаты внутри кластера.
